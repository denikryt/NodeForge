# Writing Function Library Entries

Function library entries live in `NodeForge/functions/`. Each entry is a callable operation that can be used from any NodeForge script.

## Choose the implementation style

### Pure DSL function

Use a pure DSL function when the algorithm is expressible with existing built-ins.

```text
functions/my_function/
├── __init__.py
└── source.nf
```

### DSL source with package-local helpers

Use this style when the main algorithm belongs in DSL and one small part needs Blender Python API access.

```text
functions/my_function/
├── __init__.py
├── source.nf
└── function.py
```

Common uses:

- function-specific shader/material setup
- small custom node construction helpers
- specialized data preparation for one function package

### Native backend function

Use a native backend when the whole function is more naturally generated by Python.

```text
functions/my_function/
├── __init__.py
├── source.nf
└── function.py
```

A native backend defines `compile_call(comp, expr, depth=0)` and owns compilation of the whole function call.

This style fits functions that generate large static geometry, precompute levels, or use Blender data-block APIs directly.

## Function package rules

A package name must be a valid Python-like function name:

```text
letters, digits, underscore; starts with a letter or underscore
```

Recommended layout:

```text
functions/example_function/
├── __init__.py
├── source.nf
└── function.py
```

`__init__.py` can be empty. It marks the folder as a package and keeps import behavior predictable.

## Writing `source.nf`

`source.nf` is the primary readable definition of the function.

Example:

```python
geo = input_geometry("Geometry")
scale = input_vector("Scale", default=vector(1, 1, 1))

geo = transform(geo, scale=scale)
output("Geometry", geo)
```

Guidelines:

- Declare public inputs with `input_*` built-ins.
- Use clear socket names: `Geometry`, `Scale`, `Resolution`, `Max Iter`.
- Write one or more `output(name, value)` statements.
- Keep algorithm logic visible in DSL when the built-ins can express it.
- Use package-local backend helpers for package-specific Blender API work.

## Calling another library function

Library functions can call other library functions.

```python
geo = input_geometry("Geometry")
geo = sierpinski_carpet(geo, steps=3)
output("Geometry", geo)
```

Keyword names are normalized when connected to group sockets. A keyword such as `max_iter` can match an input socket named `Max Iter`.

## Adding package-local helpers

`function.py` can expose package-local helpers through `BACKEND_BUILTINS`.

```python
from ...errors import CompileError


def compile_apply_material(comp, expr, depth=0):
    """Compile apply_material(geometry, attribute_name)."""
    # Validate arguments, compile sockets, create Blender nodes/data-blocks,
    # and return a NodeForge Value.
    ...


BACKEND_BUILTINS = {
    "apply_material": compile_apply_material,
}
```

The helper is callable from the same package's `source.nf`:

```python
geo = apply_material(geo, "my_color")
```

Helper implementation guidelines:

- Validate argument count and keywords.
- Compile DSL arguments through `comp.compile(...)`.
- Reject compile-time-only objects after dynamic argument compilation and before reading `.typ` or `.socket`. Use `reject_compile_time_object(value, "context")` from `compile_time.py`.
- Return a `Value` object or an existing helper result that returns one.
- Raise `CompileError` for user-facing errors.
- Keep helper names specific to the package when the behavior is package-specific.
- Avoid reserved embedded-system constructor names such as `ls_system`, `ls_axiom`, `ls_rule`, `ls_iterations`, `ls_angle`, and `ls_step`.

## Native `compile_call`

A native backend can compile the whole function call:

```python
def compile_call(comp, expr, depth=0):
    """Compile my_function(...) as a native function call."""
    ...
```

Use this when a function needs direct data-block generation, static level baking, or a specialized node group that would be verbose or expensive in DSL. Native `compile_call(...)` implementations receive raw AST and must guard any dynamically compiled arguments with `reject_compile_time_object(...)` before reading `.typ` or `.socket`.

## Testing a function

For every function, verify:

- the library scanner lists the function
- the function group materializes successfully
- a script can call the function by name
- expected geometry, attributes, and materials exist on evaluated output
- old library functions still compile
- any package-local helper is scoped to its package

A helper scope test should compile inside the package and fail from a normal top-level script with a clear `Unsupported function` error.
