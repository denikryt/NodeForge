# 43 — Public Rotation runtime type and defaults

**Issue:** [#56 — Rotation runtime Type support](https://github.com/denikryt/NodeForge/issues/56) · **Baseline:** `main` at `01adb4a9`, NodeForge `0.91.1`, Blender `5.2` · **Related:** [#47 — Geometry Nodes Wrapper Library](https://github.com/denikryt/NodeForge/issues/47) · **Revision:** 2 (architecture review F01–F03).

## Problem / Goal

`NFType.ROTATION`, `NodeSocketRotation` mapping, raw-node physical validation and the Extension API v2 `Rotation` marker already exist. The `.nf` public type registry omits `Rotation`; source signatures and raw `node()` type declarations therefore reject it. Shared semantic input defaults, `IRInputDeclaration`, and detached Extension API static-value inference also lack a complete Rotation contract.

Expose the existing type across typed `.nf` functions, raw nodes, Python extensions and Blender group lifecycle. A Rotation default is an XYZ Euler-angle triple **in radians**; a runtime Rotation remains distinct from a Vector. This is an enabling step for typed wrapper functions in #47, rather than an implementation of the wrapper library.

## Expected Behavior

A `.nf` function can accept, return and forward a Rotation; `node()` can select Rotation outputs; and function interfaces can supply a declared Rotation default. Extension API v2 accepts Rotation defaults and typed Rotation runtime values. Blender creates `NodeSocketRotation` interfaces and preserves their angle values through compilation and updates.

Keep **`instance_on_points` as the target #47 `nodeforge.nodes` wrapper**:

```python
# Target declaration in #47, after removing the legacy builtin:
def instance_on_points(point_geo: Geometry, instance: Geometry,
                       rotation: Rotation = (0.0, 0.0, 0.0)) -> Geometry:
    return node("GeometryNodeInstanceOnPoints",
                inputs={ID("Points"): point_geo, ID("Instance"): instance,
                        ID("Rotation"): rotation},
                output=ID("Instances"), typ=Geometry)

# Explicit runtime Vector -> Rotation conversion:
rotation = node("FunctionNodeEulerToRotation", inputs={ID("Euler"): euler},
                output=ID("Rotation"), typ=Rotation)
```

For **current #56 executable tests**, use the review's `wrap_instance_on_points(point_geo: Geometry, ...)` with the **same body**: `instance_on_points` is still a non-shadowable DSL builtin. The argument name `points` also conflicts with the separate `points()` builtin, so `point_geo` is used in both examples. After migration in #47 the intended public call is `nodes.instance_on_points(...)`; #56 does not change the builtin registry.

## Specification

1. **S01 — Public type.** The exact `Rotation` token resolves to `NFType.ROTATION` in parameter annotations (`Rotation`, `Rotation["Label"]`), single return annotations, raw `node(..., typ=Rotation)`, `node(..., outputs={"alias": Rotation})` and existing type-token consumers. It is reserved as a source type name under existing binding rules. Existing serial token `ROTATION` and the physical socket mapping retain their identities.
2. **S02 — Required inputs/outputs.** `def pass_through(value: Rotation) -> Rotation: return value` produces one `NodeSocketRotation` input and output; required parameters must be supplied at calls. A Rotation socket from a raw node or v2 extension can be forwarded through local, imported and package functions. The resulting physical links are valid.
3. **S03 — Exact runtime typing.** Rotation inputs accept runtime `Rotation` values; passing a `Vector` to a Rotation parameter or declaring a Vector physical output as `Rotation` raises `CompileError`. Existing Float-accepts-Int behavior remains unchanged. An XYZ numeric tuple **as a function default** is the declared default representation; it does not automatically convert a runtime Vector into Rotation.
4. **S04 — Default shape and source constant limits.** A declared Rotation default is an XYZ Euler-angle tuple/list of **exactly three** exact `int`/`float` components (never `bool`), in radians; negative and >2π finite values retain magnitude and order. `.nf` defaults first pass the ordinary `_const_eval()` language rules, including signed Int32 bounds for integer literals and module constants and binary32 bounds for float constants. Extension API v2 Python defaults are supplied as Python values, so an integer outside Int32 is admissible there if its float conversion satisfies S05. After validation, both surfaces store an immutable `(float, float, float)`.
5. **S05 — Numeric limits/errors.** Each evaluated component uses `normalize_float_constant`: finite, representable and quantized to binary32; reject invalid arity, nonnumeric members, `bool`, NaN, infinity and overflow. For `.nf`, also reject values that fail the prior language constant-evaluation stage (e.g. integer literal `2147483648`, float `1e50`) without bypassing that stage. Shared validation failures raise `CompileError` mentioning `Rotation default` and the invalid component index when applicable. `.nf` signature diagnostics additionally name the function parameter, including errors before normalization; Extension API declaration diagnostics identify the owning parameter. Non-compile-time defaults remain invalid.
6. **S06 — Omitted vs explicit arguments.** Omitting a Rotation parameter declared with `=` leaves the caller's group input unlinked and uses its declared default. Required Rotation parameters remain required even though Blender exposes a native unlinked value. Positional/keyword binding, panel order and function ownership work as for existing typed inputs.
7. **S07 — Extension declaration defaults.** In Extension API v2, `Rotation` parameters in `COMPILE_TIME_ONLY` or `COMPILE_TIME_OR_RUNTIME` mode may default to a three-number Python tuple/list; the normalized `ExtensionParameterSpec.default` is the canonical tuple and `default_type is NFType.ROTATION`. `RUNTIME_ONLY` still rejects defaults. Runtime values continue through the existing typed `ExtensionBackendValue`/`RuntimeRef` boundary.
8. **S08 — Type-directed extension static values.** A three-component static tuple/list in a uniquely Rotation-declared extension parameter/value leaf is interpreted as `ROTATION`; in a uniquely Vector-declared context it remains `VECTOR`. In an `NF_SET` declaring **both** Rotation and Vector, such a literal/default is ambiguous and raises a clear `CompileError`; an already typed runtime value uses its exact type. Four-component Color defaults keep their existing Color rules. In backend extension calls, candidate matching may use each candidate's parameter `TypeSpec` to resolve static operands; two equally valid Rotation/Vector overload candidates are ambiguous rather than resolved by declaration order.
9. **S09 — Physical group parity.** Blender group input/output interface sockets for `Rotation` use `NodeSocketRotation`. In Blender 5.2, a canonical numeric three-tuple can be assigned directly as the Rotation socket default; readback is an XYZ `mathutils.Euler`. Comparing its three components with the canonical tuple validates exact binary32 parity. Failed assignment or mismatch fails compilation; neither semantic IR nor detached Extension API values contain Euler objects.
10. **S10 — Persistence and update.** Input declaration metadata persists `nf_type="ROTATION"`, `socket_type="NodeSocketRotation"` and the canonical three-number default under existing input identity rules. Group creation, recompilation, source Reload, Update Script and save/reopen retain Rotation socket types, defaults and compatible external links. Any representable user-edited group-node Rotation value, **including a `1e-7` component change from zero**, survives a compatible Update Script when the script default changes; an untouched input adopts the new script default. Other types keep their existing override-detection policy.
11. **S11 — Explicit Euler conversion.** A runtime Vector is converted to a runtime Rotation through Blender's Euler to Rotation node. Existing `Object.rotation` and legacy builtins that use Euler Vector values continue to expose `Vector`. No implicit Vector↔Rotation runtime coercion is introduced.
12. **S12 — Operation scope.** Type availability is separate from operation capability. Existing Switch, Repeat, Capture, attribute and other operation-specific supported-type maps remain authoritative. `input_rotation()` and a new Rotation constructor are outside this issue; typed `def` parameters and existing raw/extension nodes provide the public entry points.

## Architecture

**A. Canonical source type boundary (S01–S03, S11–S12).** Add `"Rotation": TYPE_ROTATION` to `semantic/constants.py::TYPE_TOKEN_NAMES`. Existing readers (`function_signatures.py`, `builtin_calls.py`, `parsing.py`, `group.py`) then recognize the name consistently. Keep `source_argument_type_matches()` exact for Rotation and leave `OBJECT_PROPERTY_TYPES["rotation"]` as Vector. Reuse `blender/socket_types.py`, `blender/raw_nodes.py` and `extension_annotations.py` as they already handle exact Rotation identity. Operation-specific support remains governed by `type_capabilities.py`. **Precedent:** `plans/42_color_runtime_type_and_extension_api_v2.md` and current Color implementation use the same public-token → canonical `NFType` → typed socket path; Blender [`NodeSocketRotation`](https://docs.blender.org/api/4.4/bpy.types.NodeSocketRotation.html) declares a distinct rotation socket.

**B. Single semantic default owner and source evaluation boundary (S04–S06).** Implement a Rotation branch in `semantic/callable_contracts.py::canonicalize_group_input_default()`: accept tuple/list, length 3, exact numeric members, normalize each through `normalize_float_constant()`, return a tuple; report indexed `CompileError`. Extend `GroupInputContract.__post_init__()` and `semantic/ir.py::IRInputDeclaration.__post_init__()`. In `semantic/function_signatures.py::compile_function_signature()`, retain ordinary `_const_eval()` and its Int32/binary32 rules; when evaluating a **Rotation** default, catch its `CompileError` and rethrow with function/parameter/`Rotation default` context. Preserve the `ConstEvalUnavailable` rejection path with equivalent context. Do not introduce contextual constant evaluation to admit out-of-range `.nf` integer literals. The immutable semantic tuple belongs to the source declaration (`InputDeclarationId`) for its compilation snapshot, carried through `FunctionSignature` → IR → `GroupInterfaceContract`; panel movement does not change identity. **Precedent:** existing `_const_eval()` signed-Int32 semantics (`semantic/consteval.py`), Float binary32 normalization (`semantic/numeric_semantics.py`) and shared Float/Vector/Color canonicalizer; Blender [`mathutils.Euler`](https://docs.blender.org/api/5.2/mathutils.html) defines XYZ radians/order.

**C. Extension static dispatch (S07–S08).** Keep `TypeSpec`, `NF_SET`, `ExtensionParameterSpec`, `select_declared_nf_type()` and `RuntimeRef` as the existing canonical contracts. Extend `extensions/values.py::static_nf_type(value, declared=...)` with *declared-type-directed* handling for three-number Rotation values; reject the Rotation/Vector overlap in a declared union, preserving existing untyped three-component Vector inference and Color's four-component typed case. Existing `extensions/interface.py::_normalize_default()` then invokes shared Rotation canonicalization and stores `default_type=ROTATION`. `extensions/values.py::_canonical_static_nf()`, `pack_value()` and `unpack_value()` use the same selection for detached `NF_SET` leaves; returned detached Rotation values remain tuples. In `semantic/analysis.py::_analyze_backend_extension_call()`, resolve **static** operands against each candidate parameter's declared TypeSpec when matching overloads, after acquiring each source expression once; keep exact-first comparison for scalar Int/Float and runtime operands. Selected static values are revalidated/canonicalized using the selected parameter's TypeSpec. This removes the Color-only inference assumption at that overload boundary and handles identical-shape Rotation/Vector alternatives without implicit casting. `semantic/analysis.py`'s frontend-semantic extension path already receives a per-parameter TypeSpec and uses the shared normalization. **Precedent:** Color's detached static path (`extensions/values.py`, `extensions/interface.py`) and existing exact/compatible overload-selection logic (`semantic/analysis.py`, `tests/unit/test_extension_semantics.py`), adapted to an additional same-shape type; the TypeSpec is the contextual type owner.

**D. Physical interface, persisted values and precise Rotation overrides (S09–S10).** Follow `blender/group_assembly.py::_populate_group()` → `blender/interface.py::_create_group_input_socket()` → `_set_socket_default()` → `_record_group_input_declaration()` → `_assert_prepared_interface_parity()`. Blender 5.2 has been verified to accept canonical Rotation numeric tuples directly, so reuse the existing write path; in `blender/group_assembly.py::_assert_prepared_interface_parity()` convert the readback `mathutils.Euler` to a tuple before passing it to the shared canonicalizer. Preserve existing `INPUT_DECLARATIONS_SCHEMA_VERSION`, `InputDeclarationId` and IDProperty default encoding. In `blender/update.py::_captured_node_input_overrides()`, when an existing default entry has `nf_type == "ROTATION"`, compare the **three canonical binary32 components exactly** (the 3-component float32 socket readback tuple against the 3-component canonical persisted tuple) when distinguishing overrides from untouched values; treat malformed or non-comparable metadata conservatively as an override rather than silently discarding a user value. This is a targeted change to the decision to *capture* an override, not the existing socket identity/restore algorithm. For required Rotation inputs (`has_default=False`), compare the physical three-angle value exactly against Blender's native `(0.0, 0.0, 0.0)` default; keep `_is_zero_like_default()` for other types without declared defaults. Keep `_defaults_equal(..., eps=1e-6)` for other types. No new persistent override state or schema migration. **Precedent:** existing Color physical parity and update/rollback integration tests; the architecture review's Blender 5.2 reproduction shows that the current `1e-6` epsilon discards a representable `1e-7` Rotation edit but exact binary32 matching preserves it; Blender Rotation interface default is Euler, while semantic storage remains numeric.

**E. Boundaries and lifecycle.** No new long-lived type objects, identifiers or caches are introduced. `NFType.ROTATION` is globally stable identity; `GroupInputContract`/`IRInputDeclaration` defaults belong to one semantic compilation; extension default tuples belong to a normalized owner/registry snapshot; physical Euler values belong to Blender group/interface sockets; persisted defaults belong to the group IDProperty records. Cover direct and indirect crossings: raw result → `.nf` local/imported/package input → group output, extension result → `.nf` → extension input, semantic default → physical interface → group-node update, detached compile-time selection → extension overload, `.blend` persistence → reload and cutover. Exact socket metadata and existing runtime owner/direction validation remain enforced. No schema migration, fallback or temporary compatibility code is needed; if Blender testing reveals one, revise this plan with the required searchable marker and removal condition before implementing it.

## Implementation Steps

1. **Expose the token (S01–S03).** Extend `TYPE_TOKEN_NAMES`; update exact-map and formerly-internal Rotation assertions in `tests/unit/test_nf_types.py` and `test_raw_nodes.py`. Cover `Rotation["Label"]`, return annotations, `node()` single/named outputs, reserved identifiers, type mismatch diagnostics and absence of implicit Vector coercion.
2. **Implement defaults and contextual diagnostics (S04–S06).** Add one Rotation branch to `canonicalize_group_input_default()` using the binary32 Float helper; admit Rotation in both input-contract/IR default guards. In `compile_function_signature()`, for `typ is NFType.ROTATION` wrap `CompileError` thrown by `_const_eval()` with the parameter + `Rotation default` context **before** canonicalization, and give `ConstEvalUnavailable` the same context. Do not change numeric limits for other source expressions or add a second evaluator. Test `2147483648` and `1e50` literals failing at this earlier boundary, in-range integers, invalid components and canonical shape; compare against Python Extension defaults with independently valid large integer input.
3. **Extend typed Extension API static handling (S07–S08).** Update `static_nf_type()` to use a unique expected Rotation type for numeric 3-tuples/lists and diagnose Rotation/Vector declaration overlap. Keep Vector/Color/scalar behavior stable. Test `_normalize_default` through actual `ExtensionOwnerSession` normalized interfaces, `pack_value()`/`unpack_value()` of detached Rotation leaves, and their mismatch/stale-runtime-reference cases. Update backend extension overload analysis to match static values against candidates' `TypeSpec`s without reparsing/reevaluating the source expression; retain exact-first overload precedence and unambiguous canonical `AnalyzedStaticCallOperand` transport. Test single Rotation static arguments, Color/Vector overloads, Int/Float overloads, and ambiguous Vector/Rotation alternatives.
4. **Implement and verify Blender lifecycle (S02–S03, S09–S10).** Materialize required/default Rotation signatures, named raw outputs and `FunctionNodeEulerToRotation` → `GeometryNodeInstanceOnPoints` links in Blender 5.2, checking physical `mathutils.Euler` XYZ, component parity and `link.is_valid`. Make `blender/group_assembly.py::_assert_prepared_interface_parity()` accept the Euler readback as three components while retaining Color's four-component path. Verify the existing direct three-tuple setter on interface and Group Node sockets; no Euler-write adapter. In `blender/update.py::_captured_node_input_overrides()`, use exact canonical binary32 three-component comparison for stored `nf_type="ROTATION"` entries, including the native zero baseline of required inputs without a declared default; leave other types' epsilon comparator intact. Test a `1e-7` user edit, untouched input receiving a new script default, a larger edit, stable external links and rollback on an injected failure. Verify Reload and save/reopen with shared/unique groups.
5. **Regression/docs/release.** Extend the existing typed-boundary and extension tests; run focused and broad unit suites plus Blender integration (see Tests). Update `docs/WRITING_FUNCTIONS.md` with the single authoritative `.nf` default contract, `docs/EXTENSION_API.md` with the static/union contract, `docs/SYNTAX.md` type table and `docs/GEOMETRY_NODES_COVERAGE.md` capability row; link to the authoritative descriptions rather than duplicating them. Add changelog and bump the add-on and manifest **minor** version once, based on the then-current merged version (from `0.91.1`, target `0.92.0`), per `AGENTS.md`. No #47 wrappers are created in this change.
